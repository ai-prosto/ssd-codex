# sdd-codex — дизайн

Инструмент читает markdown-набор спеки в формате spec-runner и исполняет задачи:
агент-планировщик создаёт набор, агент-кодер проходит цикл «тест → красный прогон →
код → зелёный прогон», агент-ревьюер смотрит диф, runner коммитит. Все агенты —
OpenAI, запускаются как CLI-подпроцессы через Codex SDK.

## Устройство

### Стек и упаковка

Node.js 20+ / TypeScript, один npm-пакет с бинарём `sdd-codex`. Зависимости:
`@openai/codex-sdk` (запускает `codex` как подпроцесс), YAML-парсер конфига.
Всё остальное — свой код; внешней БД и сервера нет.

### Команды

| Команда | Что делает |
|---|---|
| `sdd-codex spec "<описание>"` / `sdd-codex spec --from-file path.md` | планировщик создаёт три файла спеки и выходит |
| `sdd-codex run [--task TASK-003] [--config path]` | исполняет задачи из готового набора |
| `sdd-codex validate` | парсит набор и печатает ошибки формата, без вызовов API |
| `sdd-codex doctor` | проверяет наличие `codex` в PATH, ключ в окружении, git-репозиторий |

### Модули

```
src/
  cli.ts            разбор аргументов, две независимые подкоманды
  config.ts         чтение и валидация sdd-codex.config.yaml
  format/
    tasks.ts        парсер tasks.md формата spec-runner (TASK-NNN, статус, поля)
    docs.ts         frontmatter и секции requirements.md / design.md
    status.ts       правка статусной строки задачи в tasks.md
  planner/
    plan.ts         команда spec: описание → три файла
    skill/          промпт-пакет планировщика под OpenAI (порт spec-generator-skill)
  agent.ts          обёртка Codex SDK: роль → подпроцесс, лог, usage
  runner.ts         порядок задач, остановка прогона, сводка
  task_loop.ts      цикл одной задачи и её прогоны (attempt)
  verify.ts         команда проверки задачи: сборка, запуск, захват вывода
  freeze.ts         проверка изменённых файлов против списка задачи, откат
  review.ts         гейт ревью: диф → вердикт
  git.ts            diff, porcelain-статус, коммит в текущей ветке
  budget.ts         счётчики ретраев, токенов и денег, решение «стоп»
  progress.ts       строки прогресса в терминале
  artifacts.ts      директория прогона, логи, report.md, run.jsonl
```

### Поток `run`

1. `config.ts` читает конфиг, `git.ts` проверяет, что дерево чистое и мы в git-репо.
2. `format/tasks.ts` читает `tasks.md`; задачи со статусом `DONE` пропускаются;
   порядок — топологический по `Depends on`, внутри — порядок в файле.
3. Для каждой задачи `task_loop.ts` крутит прогоны (attempt), каждый прогон:
   - **написание теста**: агент-кодер в режиме «только тестовые файлы разрешены»;
   - **красный прогон**: runner сам выполняет команду проверки задачи; вывод падения
     сохраняется в `red.txt`, хеш содержимого тестовых файлов фиксируется;
   - **кодинг**: агент правит разрешённые файлы; тестовые файлы уже заморожены по хешу;
   - **тест**: runner выполняет ту же команду проверки; должна пройти;
   - **заморозка**: `freeze.ts` сверяет `git status --porcelain` со списком задачи;
   - **ревью**: `review.ts` отдаёт диф агенту-ревьюеру, получает вердикт;
   - **коммит**: `git.ts` коммитит в текущей ветке, `status.ts` ставит отметку.
   Любой провал шага закрывает прогон, дерево откатывается, начинается следующий.
4. Исчерпаны ретраи или лимит бюджета — прогон останавливается целиком.

### Данные на диске

```
sdd-codex.config.yaml              единственный конфиг (трекается в репо)
spec/requirements.md               \
spec/design.md                      }  набор в формате spec-runner
spec/tasks.md                      /   (создан нами или другим приложением)
.sdd-codex/runs/<run-id>/
  run.jsonl                        события прогона машинно-читаемо
  summary.md                       сводка по прогону
  TASK-003/
    attempt-01.log                 лог прогона: промпты, вывод агента, вывод тестов
    attempt-01.red.txt             доказанный вывод падения
    attempt-01.review.json         вердикт ревьюера
    report.md                      итоговый отчёт по задаче
```
`.sdd-codex/` добавляется в `.gitignore` и исключён из проверки заморозки.

### Конфиг (пример)

```yaml
openai:
  models:
    planner:  gpt-5.1-codex      # значение передаётся в codex как есть
    coder:    gpt-5.1-codex
    reviewer: gpt-5.1-codex
  reasoning_effort: medium
run:
  max_retries: 3
  attempt_timeout_sec: 1800
verify:
  selector_runner: "uv run pytest {selectors} -q"   # как селекторы задачи превращаются в команду
  timeout_sec: 900
budget:
  max_tokens: null               # стоп выключен
  max_usd: null                  # стоп выключен
  prices_per_mtok: { gpt-5.1-codex: { input: 1.25, output: 10.0 } }
paths:
  spec_dir: spec
  artifacts_dir: .sdd-codex/runs
  context_files: [spec/requirements.md, spec/design.md]
git:
  commit_template: "{task_id}: {task_name}"
```

## Решения

#### D-01: Node.js + TypeScript, один CLI-бинарь `sdd-codex`
Codex SDK — TypeScript-библиотека, поэтому язык берём её. Один пакет, один бинарь,
без плагинов и без слоя абстракции над вендорами: читать и дорабатывать дёшево.
Платформа — macOS и Linux: только POSIX-пути, `spawn` без shell, никаких
платформенных ветвлений; Windows не поддерживаем и не имитируем.
**Функции:** FR-03, FR-10

#### D-02: Создание спеки и запуск — две подкоманды одного CLI
`sdd-codex spec` завершается после записи трёх файлов и ничего не исполняет;
исполнение начинает только `sdd-codex run`. Общего состояния между ними нет — связь
только через файлы на диске, поэтому «создать» и «запустить» нельзя перепутать.
**Функции:** FR-01, FR-02, FR-03

#### D-03: Один конфиг-файл `sdd-codex.config.yaml`, вендора в нём нет
Все настройки — в одном YAML в корне репозитория: модель отдельно для `planner`,
`coder`, `reviewer`, лимит ретраев, лимиты расхода, команды и пути. Ключа вендора
или провайдера в схеме нет вовсе: OpenAI зашит в код. Неизвестный ключ — ошибка
старта с именем ключа, чтобы конфиг не расползался молча.
**Функции:** FR-09, FR-10

#### D-04: Авторизация — только `OPENAI_API_KEY` из окружения
Своей авторизации, пользователей и ролей у инструмента нет. Ключ читается из
переменной окружения (или уже настроенной сессии `codex`), в конфиг и в артефакты
не пишется; `artifacts.ts` маскирует его в логах. `doctor` сообщает, что ключа нет,
до первого платного вызова.
**Функции:** FR-10

#### D-05: Агенты — подпроцессы `codex` через Codex SDK, роль задаёт модель и промпт
`agent.ts` — единственное место, которое порождает агентов: для каждой роли создаётся
thread Codex SDK (он поднимает `codex` как CLI-подпроцесс) с моделью из конфига,
`cwd` = корень репозитория, песочница — запись только в рабочее дерево и временный
каталог. Сеть нужна и используется только здесь, для OpenAI API. Сетевые сбои и
таймаут прогона — провал прогона (ретрай), не падение всего runner'а.
**Функции:** FR-01, FR-04, FR-06

#### D-06: Формат файлов — формат spec-runner, разбирается своим парсером
`format/tasks.ts` повторяет формат `spec/FORMAT.md` spec-runner: заголовки
`### TASK-NNN: имя`, строка приоритета/статуса (с эмодзи и без), описание,
`**Checklist:**`, `**Depends on:** / **Blocks:** / **Traces to:**`, `**Touches:**`,
`**Verifies:**`, `**Mode:**`; `format/docs.ts` читает YAML-frontmatter и секции
`REQ-NNN` / `DESIGN-NNN`, на которые ссылается `Traces to`. Полей своего изобретения
парсер не требует: незнакомые строки сохраняются и игнорируются.
**Функции:** FR-02, FR-05

#### D-07: Планировщик — порт скилла spec-generator под OpenAI
`planner/skill/` — свой промпт-пакет: системный промпт для `codex` плюс шаблоны
`requirements.template.md`, `design.template.md`, `tasks.template.md`, взятые из
`/Users/andrei/labs/spec-runner/src/spec_runner/skills/spec-generator-skill` и
переписанные под OpenAI (без Claude-специфики). Описание программы приходит
позиционным аргументом или через `--from-file`; результат — ровно три файла в
`paths.spec_dir`, после записи они прогоняются через `validate`, и расхождение с
форматом — ошибка команды, а не молчаливая запись.
**Функции:** FR-01

#### D-08: `run` работает на готовом наборе и ничего не генерирует
`run` ищет три файла в `paths.spec_dir`, парсит их и исполняет; шага планирования в
нём нет. Если файлов нет или они не разбираются — отказ с именем файла и строки,
без попытки «досоздать» набор. Требований сверх этих файлов и ключа OpenAI у `run`
нет: ни индекса, ни БД, ни предварительного `init`.
**Функции:** FR-02

#### D-09: Цикл задачи с доказанным красным тестом
Прогон задачи — четыре шага в фиксированном порядке: агент пишет тест, **runner сам**
выполняет команду проверки и сохраняет вывод падения в `attempt-NN.red.txt`, агент
пишет код, runner выполняет **ту же** команду (сравнивается строка команды) и задача
принимается только при её успехе. Тест, прошедший на красном шаге, — не доказательство:
прогон закрывается как провальный. Содержимое тестовых файлов после красного шага
фиксируется хешем, поэтому зелёный результат нельзя получить правкой теста.
**Функции:** FR-04

#### D-10: Команда проверки берётся из записи задачи
`verify.ts` берёт команду из спеки задачи: строка `**Test:**` с готовой командой либо
`**Verifies:**` со списком селекторов, которые подставляются в шаблон
`verify.selector_runner`. Задача без одного из этих полей не исполняется — она
отклоняется с указанием id, вместо подстановки «общей» команды из конфига. В конфиге
живёт только шаблон запуска, не сам предмет проверки.
**Функции:** FR-04

#### D-11: Замороженные файлы проверяются по git, а не на доверии к агенту
Разрешённый список задачи — пути из `**Touches:**` (каталог покрывает содержимое) плюс
файлы, названные её командой проверки; всё остальное дерево заморожено. После каждого
шага `freeze.ts` сравнивает `git status --porcelain` с этим списком: любой лишний
изменённый, созданный или удалённый файл — прогон не принят, дерево откатывается
(`git checkout -- . && git clean -fd` по затронутым путям), нарушение пишется в лог и
отчёт. Задача, не перечислившая файлы, отклоняется с указанием id.
**Функции:** FR-05

#### D-12: Гейт ревью — отдельный агент на модели `reviewer`
Перед коммитом `review.ts` отдельным вызовом (своя роль, своя модель, чистый thread,
без истории кодера) отдаёт ревьюеру диф `git diff HEAD`, запись задачи, красный и
зелёный вывод тестов и ждёт строгий JSON `{"verdict":"commit"|"block","comments":[…]}`.
Человека в гейте нет. `block` или нераспознанный ответ — прогон закрыт, замечания
попадают в промпт следующего прогона и прогон считается ретраем наравне с упавшим
тестом. `commit` — единственный путь к коммиту.
**Функции:** FR-06

#### D-13: Коммит в текущую ветку, ничего больше
`git.ts` умеет только `diff`, `status` и `commit` в текущем HEAD; создания ветки,
`push` и работы с PR в коде нет. Коммит делается после зелёного теста, успешной
проверки заморозки и вердикта `commit`; сообщение — по `git.commit_template` с id и
именем задачи. Перед стартом прогона грязное дерево — отказ, чтобы в коммит не попали
чужие правки.
**Функции:** FR-07

#### D-14: N ретраев на задачу, затем остановка всего прогона
`budget.ts` считает прогоны задачи; провал теста, нарушение заморозки, `block`
ревьюера и сбой агента — равноправные неудачные прогоны. После `run.max_retries`
неудач `runner.ts` останавливает прогон целиком: следующие задачи не запускаются,
в `summary.md` они помечены `not started`, код выхода — ненулевой. Выключателя у
этой остановки нет. Уже закоммиченные задачи отмечены `DONE`, поэтому повторный
`run` продолжает с места остановки.
**Функции:** FR-08

#### D-15: Лимиты расхода в конфиге, по умолчанию выключены
`run.max_retries` и `budget.max_tokens` / `budget.max_usd` задаются в том же конфиге.
Оба лимита расхода по умолчанию `null` — стоп по токенам и деньгам выключен, пока его
не включили явно. `budget.ts` суммирует usage, который возвращает Codex SDK по каждому
вызову, деньги считает по `budget.prices_per_mtok`; при превышении включённого лимита
прогон останавливается так же, как в D-14, с причиной `budget`. Накопленный расход
пишется в `run.jsonl` и в сводку всегда, даже когда лимиты выключены.
**Функции:** FR-09

#### D-16: Прогресс в терминале — строка на задачу и строка на прогон
`progress.ts` на запуск задачи печатает одну строку: id, описание, время запуска.
Под ней на каждый прогон — новая строка: номер прогона, текущий шаг
(`написание теста` / `кодинг` / `тест`) и, когда команда проверки завершилась, её
результат в той же строке. В TTY строка текущего прогона перерисовывается по смене
шага; без TTY (лог, CI) каждая смена шага печатается отдельной строкой — набор
сведений тот же. Поток вывода агента в терминал не льётся, он идёт в лог прогона.
**Функции:** FR-11

#### D-17: Поддиректория на задачу: лог на прогон и итоговый отчёт
`artifacts.ts` создаёт `.sdd-codex/runs/<run-id>/<TASK-id>/`: `attempt-NN.log`
(промпты, ответ агента, вывод команд), `attempt-NN.red.txt`, `attempt-NN.review.json`
и `report.md` — итог по задаче: команда проверки, список разрешённых файлов, по
каждому прогону шаг и причина провала, вердикты ревьюера, коммит, расход. Отчёт
пишется и при успехе, и при провале. Рядом `run.jsonl` и `summary.md` по прогону.
**Функции:** FR-12

#### D-18: Отметка о выполнении — в самом `tasks.md`
После коммита `format/status.ts` правит статусную строку задачи на месте
(`⬜ TODO` → `✅ DONE`, без эмодзи — `TODO` → `DONE`), сохраняя остальную строку и
файл байт-в-байт; правка входит в тот же коммит задачи. Так отметка видна и в
исходном наборе, и служит точкой продолжения после остановки прогона.
**Функции:** FR-07, FR-12

#### D-19: Локальная система — только рабочее дерево репозитория
Runner читает описание программы, markdown-набор и код репозитория; пишет файлы
набора, код, тесты, логи/отчёты в `.sdd-codex/` и делает git-коммиты. Пути
нормализуются и проверяются на выход за корень репозитория: `..`, абсолютные пути и
симлинки за пределы дерева отклоняются. `.sdd-codex/` в `.gitignore` и вне проверки
заморозки; за пределы репозитория (кроме временного каталога подпроцесса) не пишем.
**Функции:** FR-05, FR-12

#### D-20: Каждый пользователь запускает у себя, общего состояния нет
Пользователи — автор и коллеги, каждый в своём клоне: конфиг трекается в репо,
секрет — в окружении (D-04), артефакты прогона локальны и не коммитятся, сервера и
общей базы нет. Установка — `npm i -g` или `npx` плюс установленный `codex`;
`doctor` печатает одним экраном, чего не хватает, чтобы коллеге не приходилось
читать код.
**Функции:** FR-10

#### D-21: Порядок задач — зависимости, затем порядок в файле
`runner.ts` строит порядок топологической сортировкой `Depends on` со стабильным
тай-брейком по позиции в `tasks.md`; цикл зависимостей или ссылка на несуществующий
id — ошибка до первого платного вызова (та же проверка в `validate`). Задача с
незавершённой зависимостью не запускается.
**Функции:** FR-02, FR-08

## Открытые вопросы

- Точный формат и взаимные ссылки файлов спеки / требований / задач: нужно сверить с
  spec-runner (`spec/FORMAT.md`, `schemas/spec-frontmatter.schema.json`, шаблоны
  скилла) и зафиксировать как контракт — какие поля обязательны, какие имена файлов
  ожидаются по умолчанию, как именно задача ссылается на требования и дизайн.
- В spec-runner `**Touches:**` — прогноз, который ничем не сверяется; в sdd-codex это
  исполняемый список заморозки (D-11). Нужно проверить на реальных наборах от других
  приложений, всегда ли это поле там есть, и если нет — договориться, каким полем
  готовые наборы объявляют список файлов задачи.
- Чем в готовых наборах задаётся команда проверки задачи (D-10): `**Verifies:**`
  селекторами, отдельным полем или иначе — зависит от того же контракта формата.
